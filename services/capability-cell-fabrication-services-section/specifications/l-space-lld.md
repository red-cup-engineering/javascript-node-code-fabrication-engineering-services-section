# LS-LLD-001 — Specification lineage at the existing CapCell fabrication boundary

**Stage/format distinction.** The Group admits **Requirements → Specification → Architecture → Design → Fabrication** as five distinct engineering decisions. This `LS-LLD-001` is a detailed **design** artifact, *not* the sole Design gate; `LS-HLD-001` is historically named high-level design containing architecture views, but **Architecture ≠ HLD**; `LS-SAS-001` is a legacy-named semantic specification, not a general System Architecture stage. The exact CapCell v2 `sas/hld/lld` lineage is an existing **three-source byte-integrity protocol**. It cannot show that the customer's Requirements admission was received, a complete [ISO 42010](https://www.iso.org/standard/74393.html)/[arc42](https://arc42.org/overview/) architecture description was accepted, or a physical/software artifact was fabricated and independently delivered. The normative [Group engineering method](https://github.com/561-group/561-group-services-section/blob/main/content/text/glossary/concepts/method-for-work-in-the-561-group.md) governs those separately. **Do not rename, delete, alias, or reinterpret live `sas/hld/lld` keys as a shortcut:** preserve the opted-in v2 consumer contract until an explicitly versioned, fully qualified replacement has actual receiving.

**Authority:** [LS-SAS-001](https://github.com/lenticule-science/linguistics-services-section/blob/main/specifications/l-space-semantic-architecture.md) → [LS-HLD-001](./l-space-hld.md) → this contract → [actual fabrication implementation](../services/capcell-manifest-fabrication-service/src/fabricate-local-capcell.mjs). The first two retain ownership of meaning and responsibility; this LLD defines a **finite executable interface** and its tests. It does **not** create another term registry, another compiler, another provider market or a new `sources.json` ledger.

## 1. Versioned wire shape

Existing v1 stays legal and byte-compatible. The new opt-in profile `org.red-cup-engineering.capcell.v2` adds **one** mandatory `lineage` field to the otherwise unchanged `CapCellSpecification`.

```ts
interface SourcePin {
  uri: string;        // absolute HTTPS resource, without credentials or fragment
  revision: string;   // source-native immutable revision, not implicit latest/main
  sha256: string;     // 64 lowercase hex chars: SHA-256 of the exact UTF-8/binary source bytes
}
interface Lineage {
  sas: SourcePin;     // existing v2 key: historically named semantic specification source (not requirements-stage approval)
  hld: SourcePin;     // existing v2 key: historically named high-level-design/architecture-view source (not an architecture certificate)
  lld: SourcePin;     // existing v2 key: detailed design/interface/test source (not a complete design admission)
}
interface CapCellV2 {
  profile: "org.red-cup-engineering.capcell.v2";
  identity: CapCellSpecification["identity"];
  package?: CapCellSpecification["package"];
  capability: CapCellSpecification["capability"];
  materials?: CapCellSpecification["materials"];
  lineage: Lineage;
}
```

The `lineage` value is part of the SEN-normalized CapCell specification identity, not a detached JSON filename. Its `sas`/`hld`/`lld` keys retain their exact legacy v2 wire interpretation, and **full requirement/specification/architecture/design/fabrication evidence remains separately qualified**. Sources remain at their own URLs/revisions. **Do not embed papers, entire upstream documents, credentials, workspace layout or customer-private material into this value.**

`SourcePin` identifies bytes but does **not** assert those bytes' scientific truth, source ownership, license, conformance or customer authorization. Research article references and precise Lean declarations belong in the authoritative SAS document, not as repeated pseudo-research under each code generator. A program is not made correct by a paper citation.

## 2. Typed seam and semantics

Keep `normalizeCapCellSpecification(source)` synchronous and pure. On v2, validate exact keys, nonempty distinct source pins, URL shape and revisions, canonical lowercase SHA-256; normalize every field. The existing `identifyNormalizedSemanticContent` continues to assign the specification's identity. V1 normalization must never begin requiring a lineage property; v1 must continue rejecting arbitrary extra fields.

The existing `fabricateLocalCapCell(source, evidence)` remains synchronous and **shall not pretend it has read remote sources**. For v2 without source readback it emits an `unrealized` candidate with typed `missing` defects for all three `lineage:sas:unverified`, `lineage:hld:unverified`, `lineage:lld:unverified`. It may also report its usual unbound provider cells. The candidate retains exact source-pin declarations and the manifest's SEN/NI identity.

Add one **bounded verified-read seam** to the existing fabricator (not an EDA subsystem): `fabricateVerifiedCapCell(source, evidence, readLineage)` with `readLineage({kind,uri,revision})` supplied by the authorized source provider/adapter and returning exact `Uint8Array`/Buffer bytes. Verify SHA-256 over the received bytes *before* candidate realization. An absent callback, thrown provider read, untrusted return type, mismatched digest, repeated source URI, invalid path or forgotten revision shall either **refuse explicitly** or leave the v2 candidate `unrealized`. Never silently substitute `main` or an archived L-Space corpus. A result returned by the callback is a **source-integrity observation only**, not independent validation of the author's claims. The source adapter must retain provider attribution outside this pure reader; any stronger authenticity statement needs a separate credentialled provider receipt.

`writeLocalCapCellBundle(source, outputDirectory, evidence, options?)` remains the existing output writer, with optional `{readLineage}`. It calls the verified-read seam for v2 only when the reader is supplied, otherwise emits an unrealized candidate (not a secretly trusted complete one). No new file is created for the graph of references: `capcell.spec.cbor`, `capcell.manifest.cbor`, `capcell.manifest.json` are existing projections. A `manifest.lineageIntegrity` status distinguishes `unverified` from `digest-verified`; the latter is not accepted/installed.

**No tacit upgrade of v1**: source/SDK consumers intentionally staying on `capcell.v1` retain their historical contract. Widening the deployment admission policy to mandate v2 is a separate, versioned Coesite/consumer receiving event after the new tests and source providers exist.

## 3. Hoare and ribosome correspondence — precise boundaries

The code's work contract has precondition `P`: all required caller inputs type-check, the operative law is NI-addressed, the source chain is pinned/admitted, the requested effect belongs to exactly one cell, and the caller possesses proper authority. Execution body `Q`: reuse the PDK's existing normalization, content identity, provider binding, fabricator and refusal logic; an LLM may supply candidate *text* only through this typed admission. Postcondition `R`: an immutable, attributable candidate bundle exists; its manifest says which requirements/provider bindings were verified and which were not. **R does not imply deployed, paid, scientifically accepted or customer received.**

Composition with a deployment cell requires an independently witnessed `post_fabrication ⇒ pre_deployment`. The readback from deployment must be compared with the *original consumer* acceptance condition. This is the engineering realization of the [Rendanheyi-Hoare research](https://drive.google.com/file/d/1U0gIK1eRgHD_SxdArnjWaopKZisUi8eV/view) and [work-order/ribosome hypothesis](https://drive.google.com/file/d/1CzMBsrl9lq9X43kteNSfG2SRegAxIF2e/view), not a proof that model behavior is deterministic. Claims about free-energy protein folds or electronically designed circuitry are outside this software-only proof obligation.
